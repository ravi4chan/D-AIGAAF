# D-AIGAAF — Data Governance

## 1. Purpose

This document defines the governance requirements for managing data used, generated, exchanged, or relied upon by defence AI capabilities.

Data governance establishes clear ownership, accountability, permitted use, quality expectations, access controls, lifecycle controls, and assurance responsibilities.

The objective is not to make all data perfect. It is to ensure that data is **appropriate, understood, controlled, protected, and sufficiently trustworthy for its intended mission and consequence level**.

---

## 2. Core Principle

> **Data ownership and governance must remain explicit throughout the AI lifecycle; technical access to data does not constitute authority to use it.**

Every consequential data asset should have:

- an identified owner
- a defined purpose
- defined permitted uses
- appropriate access controls
- known limitations
- lifecycle controls
- traceability
- assurance evidence proportionate to risk

---

## 3. Scope

This document applies to:

- training data
- validation and test data
- operational data
- sensor data
- intelligence and information inputs
- reference data
- geospatial data
- human-generated data
- synthetic data
- labelled and annotated datasets
- data generated by AI systems
- AI outputs reused as information inputs
- logs and audit data
- supplier-provided data
- shared or exchanged data
- data retained for assurance, investigation or lessons learned

It applies throughout:

**Acquisition → Development → Integration → TEVV → Deployment → Employment → Monitoring → Change → Revalidation → Retirement**

---

## 4. Governance Objectives

Data governance should ensure that:

1. Data has a defined purpose.
2. Ownership and accountability are known.
3. Permitted use is understood.
4. Access is controlled.
5. Data quality is assessed.
6. Provenance is traceable.
7. Material limitations are documented.
8. Data integrity is protected.
9. Changes are controlled.
10. Data dependencies are visible.
11. Data-related risks are assessed.
12. Evidence is retained.
13. Data can be withdrawn or restricted when necessary.
14. Data remains fit for its authorised use.

---

## 5. Data Governance Principles

### 5.1 Purpose Limitation

Data should be collected, acquired, processed and used for defined purposes.

Use beyond the original purpose should be assessed for:

- mission relevance
- legal and policy implications
- security
- privacy or other applicable information-handling requirements
- operational risk
- assurance impact

### 5.2 Accountability

Every material data asset should have an accountable owner.

Responsibility should not become ambiguous merely because data passes between organisations, systems or suppliers.

### 5.3 Risk Proportionality

Governance should increase with:

**Consequence × Mission Criticality × Data Dependence × Exposure**

Low-consequence data should not require the same controls as data influencing high-consequence operational decisions.

### 5.4 Traceability

Material data should be traceable from source through processing to use.

### 5.5 Integrity

Data used by consequential AI should have appropriate mechanisms to detect corruption or unauthorised alteration.

### 5.6 Transparency of Limitations

Known limitations should be documented rather than hidden by aggregated quality scores.

### 5.7 Lifecycle Control

Data should remain governed from creation or acquisition through final retention or disposal.

---

## 6. Data Ownership Model

### 6.1 Data Owner

The Data Owner is accountable for the purpose, permitted use and governance of a data asset.

Responsibilities include:

- defining purpose
- approving permitted uses
- identifying sensitivity and handling requirements
- approving access principles
- identifying material risks
- ensuring lifecycle decisions are made
- approving significant changes where required

### 6.2 Data Steward

The Data Steward manages the operational governance of the data asset.

Responsibilities include:

- metadata
- quality monitoring
- lineage
- validation
- access administration
- issue management
- change records
- coordination with technical teams

### 6.3 AI System Owner

The AI System Owner is accountable for understanding how the capability depends on data.

Responsibilities include:

- identifying critical data dependencies
- ensuring data requirements are documented
- assessing operational data limitations
- ensuring data changes are assessed
- maintaining linkage between data and system assurance

### 6.4 AI Developer / Model Owner

Responsibilities include:

- documenting development data
- maintaining reproducibility
- identifying data limitations
- documenting preprocessing and transformations
- supporting data-related TEVV
- reporting material data issues

### 6.5 Operational AI Advisor

The OAIA provides operationally informed advice on whether data conditions remain appropriate for the intended mission.

The OAIA may advise on:

- operational relevance
- data limitations
- unusual or degraded data conditions
- changes in data environment
- implications for autonomy
- need for escalation or revalidation

The OAIA does not replace the Data Owner, technical authority, assurance function or operational authorising authority.

### 6.6 Assurance / TEVV Function

Provides independent assessment, where appropriate, of:

- data quality
- provenance
- representativeness
- integrity
- operational suitability
- data-related failure modes
- evidence sufficiency

### 6.7 Operational Authorising Authority

Determines whether residual data-related risk is acceptable within the proposed operational authority.

## 7. Data Asset Registration

Material data assets should be registered.

A Data Asset Record should identify, where applicable:

| Field | Description |
|---|---|
| Data Asset ID | Unique identifier |
| Name | Human-readable name |
| Owner | Accountable owner |
| Steward | Operational custodian |
| Purpose | Intended use |
| Source | Origin of data |
| Classification / Handling | Applicable controls |
| Quality Status | Current assessment |
| Provenance Status | Traceability level |
| Integrity Status | Integrity controls |
| Criticality | Operational importance |
| AI Dependency | Systems/models dependent on it |
| Version | Current approved version |
| Change Status | Current change state |
| Retention | Retention requirements |
| Disposal | Disposal requirements |

## 8. Data Classification and Handling

Data governance should align with applicable national, defence, legal and organisational classification and handling requirements.

The governance process should establish:

- who may access the data
- where it may be stored
- how it may be transferred
- how it may be processed
- whether it may be used for AI training or evaluation
- whether it may be shared externally
- how copies are controlled
- how disposal is performed

Classification should not be treated as the only measure of data risk.

Unclassified data can still be operationally critical, misleading, integrity-sensitive or mission-dependent.

---

## 9. Data Access Governance

Access should follow:

**Need → Authority → Least Privilege → Authentication → Monitoring → Review**

Access decisions should consider:

- role
- mission requirement
- data sensitivity
- consequence
- environment
- system security
- duration of access
- supplier or third-party status

Privileged access should receive enhanced controls and monitoring.

Access should be reviewed when roles, missions, systems or data requirements change.

---

## 10. Data Use Authorisation

Access to data and authority to use data are distinct.

A user or system may technically access a dataset but still be prohibited from using it for:

- a different mission
- a different model
- a different operational environment
- a different autonomy level
- a different organisation
- a different purpose

Where data use can materially affect AI behaviour or operational risk, the permitted use should be explicitly documented.

---

## 11. Data Quality Governance

Data quality should be assessed against intended use.

Relevant dimensions include:

- accuracy
- completeness
- consistency
- validity
- timeliness
- relevance
- representativeness
- uniqueness
- provenance
- integrity

Quality thresholds should be linked to mission consequence where practical.

For example, a minor data-quality issue may be acceptable for exploratory analysis but unacceptable where the same data influences a high-consequence operational decision.

---

## 12. Data Provenance Governance

For material datasets, governance should establish:

**Source → Collection → Processing → Transformation → Storage → Transfer → Use**

The organisation should record, where feasible:

- originating source
- collection method
- collection time
- responsible organisation
- processing steps
- transformations
- labelling
- version
- transfer history
- downstream use

Unknown provenance should be treated as a limitation.

---

## 13. Data Lineage

Data lineage should enable reconstruction of how information changed.

Lineage should cover, where relevant:

- source systems
- ingestion
- preprocessing
- filtering
- labelling
- aggregation
- transformation
- augmentation
- model input
- model output
- downstream systems

For high-consequence capabilities, lineage should be sufficiently detailed to support investigation and assurance.

---

## 14. Data Quality Issues

Material data issues should be recorded and managed.

Examples include:

- inaccurate records
- missing information
- stale information
- inconsistent sources
- incorrect labels
- corrupted records
- unknown provenance
- unrepresentative samples
- unexpected distribution changes

Each material issue should have:

- issue identifier
- description
- affected data
- affected systems
- risk assessment
- owner
- corrective action
- disposition
- closure evidence

---

## 15. Data Change Governance

Changes to data or data-processing pipelines should be controlled.

Changes may include:

- new sources
- source replacement
- sensor changes
- collection-method changes
- preprocessing changes
- labelling changes
- schema changes
- reference-data changes
- pipeline changes
- distribution changes
- retention changes

The governance response should depend on potential impact, not merely the size of the technical change.

---

## 16. Data Change Classification

A working classification may be:

### Class 0 — Administrative

No meaningful effect on data meaning, integrity or AI behaviour.

### Class 1 — Minor

Limited change with low expected operational impact.

### Class 2 — Controlled

Change that requires documented testing or verification.

### Class 3 — Material

Potential to alter AI behaviour, performance, risk or authorised conditions.

### Class 4 — Critical

Potential to materially affect high-consequence operation, autonomy, safety, security or operational authority.

Material and critical changes should trigger appropriate impact assessment and may require revalidation or reauthorisation.

---

## 17. Data Governance and AI Development

Development teams should be able to identify:

- which data trained the model
- which data was used for validation
- which data was used for testing
- what transformations were applied
- what exclusions were made
- what limitations exist
- what data assumptions affect performance

Data used to demonstrate model performance should be traceable to the relevant model and configuration baseline.

---

## 18. Data Governance and TEVV

TEVV should assess whether data is appropriate for the assurance claim being made.

Governance should support assessment of:

- representativeness
- data leakage
- label quality
- edge cases
- adversarial conditions
- environmental variation
- degraded conditions
- operational distribution
- data transformations

A high benchmark result on unsuitable data should not be treated as evidence of operational readiness.

---

## 19. Data Governance and Operational Employment

Operational use should remain within the data conditions for which the capability was assessed and authorised.

Monitoring should identify:

- data quality deterioration
- source changes
- sensor degradation
- stale inputs
- distribution shift
- unexpected data sources
- conflicting information
- integrity anomalies

Material changes may require operational restriction, revalidation or reauthorisation.

---

## 20. Data Governance and Human Decision-Making

Where AI supports consequential decisions, data limitations should be visible to appropriate human decision makers.

The objective is to allow the decision maker to understand:

- what information the AI relied upon
- how current it is
- whether sources conflict
- whether important information is missing
- whether the data falls outside validated conditions
- how much confidence should reasonably be placed in the output

The AI should not create a false impression of certainty merely because its output is presented in a definitive form.

---

## 21. Data Governance and Autonomy

Data conditions can constrain permissible autonomy.

Examples include:

- reduced sensor coverage
- unreliable communications
- uncertain environment
- stale information
- conflicting inputs
- unexpected data distributions

Where data conditions deteriorate beyond the validated envelope, the system may need to:

- reduce autonomy
- require additional human confirmation
- restrict functions
- transfer to human-only operation
- enter a safe state
- suspend operation

Any such behaviour should be defined, tested and authorised.

---

## 22. Data Governance and Information Integrity

Data governance should distinguish between:

**Data correctness** and **information trustworthiness**.

A technically valid dataset may still produce misleading information if:

- the context is missing
- the source is unreliable
- the information is stale
- multiple sources conflict
- adversarial manipulation is suspected
- important uncertainty is omitted

Information integrity should therefore be treated as an operational assurance concern.

---

## 23. Data Security and Integrity

Data governance should work with **06 AI Security** to address:

- unauthorised access
- data manipulation
- malicious injection
- compromised sources
- pipeline compromise
- unauthorised copying
- insecure transfer
- integrity failures
- compromised dependencies

Security controls should be proportionate to consequence and exposure.

---

## 24. Third-Party Data Governance

Supplier and third-party data should be assessed before consequential use.

Assessment should consider:

- provenance
- ownership
- permitted use
- collection methodology
- quality
- representativeness
- integrity
- update process
- dependencies
- security
- known limitations

Supplier assurance should not automatically be treated as independent assurance.

---

## 25. Data Sharing Governance

Before sharing material data, governance should establish:

- purpose
- recipient
- authority
- permitted use
- handling requirements
- security requirements
- integrity requirements
- retention
- downstream responsibilities

Where shared data can affect consequential AI behaviour, the receiving organisation should assess its suitability for the intended use.

---

## 26. Data Retention

Retention periods should consider:

- operational need
- legal and policy requirements
- auditability
- assurance
- incident investigation
- lessons learned
- security
- historical reconstruction

Critical lifecycle evidence should not be destroyed merely because the underlying model or system has been retired.

---

## 27. Data Disposal

Disposal should be controlled and, where necessary, verified.

The organisation should consider:

- active copies
- backups
- replicas
- cached copies
- derived datasets
- model-embedded information
- supplier-held copies
- archived records

Disposal requirements should be documented before final closure.

---

## 28. Data Incidents

A data incident may include:

- unauthorised access
- unauthorised modification
- data loss
- corruption
- malicious manipulation
- poisoning
- provenance failure
- integrity failure
- inappropriate use
- unexpected data exposure
- material quality failure

Incidents should be assessed for effects on:

- AI behaviour
- mission performance
- human decision-making
- safety
- security
- autonomy
- operational authorisation

Where necessary, the affected capability should be restricted or suspended pending assessment.

---

## 29. Data Risk Management

Data risks should feed the wider D-AIGAAF risk process.

A useful conceptual model is:

**Data Risk = Consequence × Data Dependence × Data Uncertainty × Exposure**

Risk assessment should consider:

- likelihood
- impact
- detectability
- reversibility
- duration
- affected missions
- affected autonomy
- affected systems
- evidence confidence

---

## 30. Data Governance and Operational Authorisation

Operational authorisation should identify material data conditions.

These may include:

- approved data sources
- minimum data quality
- freshness
- required provenance
- permitted data types
- required integrity controls
- acceptable degraded conditions
- monitoring thresholds
- prohibited data conditions

A change in these conditions may require reassessment of operational authority.

---

## 31. Data Governance Decision Rights

Decision rights should be explicit.

| Decision | Primary Accountability |
|---|---|
| Data purpose | Data Owner |
| Data access | Data Owner / authorised data governance function |
| Data quality | Data Steward |
| Data architecture | Technical authority |
| Data suitability for AI | AI System Owner + relevant assurance functions |
| Data-related TEVV | TEVV / Assurance Function |
| Data risk acceptance | Authorised risk authority |
| Operational use | Operational Authorising Authority |
| Material data change | Designated change authority |
| Data-related suspension | Authorised operational authority |
| Data retirement/disposal | Data Owner + relevant authority |

Specific organisational titles may differ; the decision rights should remain explicit.

---

## 32. Data Governance Records

At minimum, consequential capabilities should maintain links between:

- Data Asset Record
- Data Source Record
- Data Provenance Record
- Data Quality Record
- Data Lineage Record
- Data Access Record
- Data Change Record
- Data Incident Record
- Data Assurance Record

These should connect to the broader lifecycle records.

---

## 33. Governance Review

Data governance should be periodically reviewed and event-driven when:

- mission changes
- data sources change
- operational environments change
- model behaviour changes
- incidents occur
- new vulnerabilities emerge
- supplier arrangements change
- legal or policy requirements change
- data quality materially deteriorates

Review frequency should be risk-proportional.

---

## 34. Common Governance Failure Modes

- No clearly accountable data owner.
- Treating technical access as permission to use.
- Assuming supplier ownership removes organisational responsibility.
- Failing to document data provenance.
- Treating data quality as a single numerical score.
- Ignoring operational data drift.
- Using non-representative data to justify operational claims.
- Changing data pipelines without impact assessment.
- Allowing data limitations to disappear from AI outputs.
- Retaining uncontrolled copies after retirement.
- Failing to connect data governance to operational authorisation.
- Treating data security separately from AI security.
- Failing to reconstruct which data influenced a consequential decision.

---

## 35. Core Rules

1. **Every material data asset should have an accountable owner.**
2. **Access does not automatically constitute authority to use.**
3. **Data governance must be proportionate to operational consequence.**
4. **Data provenance and lineage should be maintained for consequential use.**
5. **Data quality must be assessed against intended purpose.**
6. **Material data changes require impact assessment.**
7. **Data limitations must remain visible to appropriate decision makers.**
8. **Critical data dependencies must be identified.**
9. **Third-party data does not transfer accountability for its use.**
10. **Operational data conditions must be included in assurance.**
11. **Data-related incidents can invalidate AI assurance and operational authority.**
12. **Data governance must connect to the D-AIGAAF Golden Thread.**

---

## 36. Golden Thread

Data governance contributes to:

**Mission Need → Risk → Requirements → Data Dependency → Controls → Testing → Evidence → Assurance → Authority → Employment → Monitoring → Change / Incident → Revalidation → Reauthorisation → Retirement → Decommissioning**

The governance objective is to maintain a defensible relationship between:

**Why the data is used → Who controls it → How it is protected → What limitations exist → How it affects AI behaviour → What operational authority depends upon it**

## 38. Summary

D-AIGAAF treats data governance as an operational assurance function rather than a purely administrative or technical activity.

The essential governance chain is:

**Purpose → Ownership → Access → Quality → Provenance → Integrity → Use → Monitoring → Change → Assurance → Operational Authority**

For consequential defence AI, the governing question is:

> **Can the organisation demonstrate who controls the data, why it is being used, whether it is fit for the authorised purpose, what limitations exist, and how those limitations affect operational risk and authority?**

If the answer cannot be demonstrated with appropriate evidence, the limitation should flow into risk, assurance, operational restrictions and, where necessary, revalidation or reauthorisation.
