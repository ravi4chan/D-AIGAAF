# 25-Implementation and Programme Templates

## Purpose

This document provides reusable templates for implementing D-AIGAAF as an organisational capability rather than treating it as a collection of documents or isolated compliance activities.

Implementation connects the framework to people, processes, technology, governance, assurance, acquisition, operational commands, suppliers, and existing enterprise systems.

## Core Principle

**D-AIGAAF implementation is a capability-building programme, not a documentation exercise.**

An organisation should be able to demonstrate that D-AIGAAF changes how consequential AI capabilities are identified, assessed, developed, acquired, tested, authorised, employed, monitored, changed, and retired.

## Implementation Chain

**Baseline → Scope → Prioritise → Design → Assign → Build → Pilot → Assure → Institutionalise → Measure → Improve**

## Programme Outcome

Successful implementation should establish an organisational system in which:

- consequential AI capabilities are identifiable;
- missions and use cases are defined before governance decisions;
- risk is consequence-based;
- autonomy is explicitly classified and bounded;
- human authority is identifiable and meaningful;
- TEVV produces decision-relevant evidence;
- operational authorisation is explicit;
- operational conditions are controlled;
- continuous assurance is maintained;
- incidents and failures trigger governance action;
- changes trigger proportionate reassessment;
- evidence and records are traceable;
- suppliers and dependencies are governed;
- workforce competence and capacity are addressed;
- retirement is controlled;
- lessons continuously improve the system.

# Implementation Maturity Gates

Implementation should pass progressively stronger gates rather than being declared complete merely because documents exist.

## Gate 1 — Foundation

The organisation can identify:

- Who governs AI
- Which AI capabilities exist
- Which missions they support
- Who owns risk
- Who has authority

## Gate 2 — Controlled

The organisation can:

- Assess risk
- Classify autonomy
- Define human authority
- Apply lifecycle controls
- Establish security requirements
- Conduct TEVV

## Gate 3 — Operational

The organisation can:

- Authorise AI for defined missions
- Control operating environments
- Monitor operational employment
- Detect incidents
- Intervene
- Manage degraded operation
- Control changes

## Gate 4 — Assured

The organisation can:

- Maintain continuous assurance
- Produce reliable evidence
- Conduct independent challenge
- Revalidate after material changes
- Reauthorise when required
- Demonstrate traceability

## Gate 5 — Adaptive

The organisation can:

- Learn from incidents
- Benchmark maturity
- Improve controls
- Adapt to new AI architectures
- Respond to emerging threats
- Update governance without losing accountability

# Implementation Anti-Patterns

D-AIGAAF implementation should actively avoid:

1. **Documentation-first implementation** — producing templates without changing decisions.
2. **Compliance theatre** — treating completed forms as proof of safety or assurance.
3. **Technology-first governance** — governing systems without understanding missions and consequences.
4. **One-size-fits-all controls** — applying identical controls regardless of consequence or autonomy.
5. **Parallel bureaucracy** — creating duplicate processes where existing enterprise controls can be adapted.
6. **Authority ambiguity** — assuming responsibility exists because an organisation or system owner has been named.
7. **Human-in-the-loop theatre** — treating nominal human presence as meaningful control.
8. **Maturity inflation** — declaring high maturity without evidence of effective implementation.
9. **Metric substitution** — treating dashboard metrics as assurance.
10. **Pilot exceptionalism** — allowing pilots to bypass governance without explicit bounded exceptions.
11. **Supplier outsourcing of accountability** — assuming supplier assurance transfers operational responsibility.
12. **Static implementation** — failing to account for changing AI capabilities, threats, missions, regulations, and environments.
13. **Framework accumulation** — adding standards and controls without resolving conflicts or duplication.
14. **Ignoring retirement** — implementing governance for deployment but not for withdrawal and decommissioning.

# Implementation Success Test

A D-AIGAAF implementation should be challenged with the following question:

> **If a consequential AI capability were proposed tomorrow, could the organisation reliably identify the mission, consequence, risk, autonomy, human authority, requirements, controls, evidence, TEVV, operational conditions, authorisation, monitoring, change triggers, incident response, and eventual retirement path without inventing a process from scratch?**

If the answer is no, implementation is incomplete.

**D-AIGAAF succeeds when governance becomes a repeatable organisational capability embedded in real decisions, systems, people, contracts, technical controls, operational processes, evidence, and accountability—not when the framework merely exists as a set of documents.**
